# 0.2 -- Introducción de programas y lenguajes de programación



Computadoras modernas son increíblemente rápidas, y son están volviendo mas rápidas todo el tiempo. A pesar de que las computadoras también tienen algo que los ata: computadoras solo saben un cierto y limitado lista de comandos/instrucciones, y deben de ser intuidas en que es exactamente lo que se debe de hacer.



Un Programa de Computadora es una secuencia de instrucciones que dirige a una computadora para llevar a capo un secuencia de acciones de una forma especifica. Programas de computadoras típicamente son escritas en un lenguaje d programación. el cual el lenguaje esta diseñado para facilitar las instrucciones para aprender a escribirla para comunicarte con la computadoras. Hay bastantes tipos de programas de lenguajes de programación, y cada una de ellas atiende a una cierta cantidad de necesidades, El acto(y arte) de programar se llama programación. Estaremos hablando sobre específicamente como crear programas en C++ in lecciones por venir en este capitulo.



Cuando una computadora esta llevando a cabo las acciones descritas por las instrucciones de un programa de computadora, decimos que esta corriendo o esta ejecutando el programa. Una computadora no comenzara la ejecución de un programa al menos que sea ordenada a que lo haga. Eso típicamente requiere que el usuario lanza( o corra o ejecute) el programa, aunque programas pueden ser ejecutadas por otros programas.



Programas son ejecutadas en el hardware de la computadora, El cual consiste de los componentes físicos que componen a una computadora, Hardware notable encontrada típicamente en un dispositivo para computación incluyen:



* un CPU (unidad central de procesamiento, usualmente llamado el "cerebro" de la computadora), El que de hecho ejecuta los programas instruidos.



* Memorias, donde información de como ejecutar programas son guardadas entes de su ejecución



* Dispositivos Interactivos (ej.. un monitor, pantalla táctil, teclado, o ratón), el cual permite que una persona interactúe con la computadora.



* Dispositivos de Almacenamiento (ej.. un disco duro, SSD, o flas de memoria), que retenga información ( incluyendo programas instalados) incluso cuando la computadora esta apagada.



En contraste, el termino software se abarca a los programas en el sistema que son diseñados para ser ejecutados en el hardware.



En computación moderna, programas usualmente interactúan con mas que con solo el hardware -- ellos también interactúan con otros softwares en el sistema (particularmente el sistema operativo). El termino plataforma se refiere a un conjunto de hardware y software ( OS, browser, etc...) que proporciona el entorno que un software ocupa para correr. Por ejemplo, el termino "PC" es usado coloquialmente para referirse a una plataforma consistente de un Windows OS corriendo en un x86-familia CPU.



Plataformas usualmente ofrecen servicios útiles para los programas que se encuentren corriéndolos. Por ejemplo, una aplicación de computador de escritorio pueda solicitar que el sistema operativo le de un cacho de memoria gratis, crea un nuevo folder por allá, o toque un soindo. el programa ejecutándolo no necesariamente nessecita saber como realmente esto es facilitado. Si un programa usa funcionalidades o servicios provisionados por la plataforma, se vuelve dependiente en esa plataforma, y no puede ser ejecutada en otras plataformas sin ser modificada. Un programa que es fácilmente transportada de una plataforma a otra se dice que es portable. El acto de modificar un programa para que pueda correrse en otra plataforma se llama porting.



Ahora que hemos hablado de sobre programas, debemos discutir lenguajes de programación. Esto no solo será una lección de historia, también estaremos introduciendo terminología que vendrá en futuras lecciones.



## MACHINE LEARNING



El CPU de una computadora es incapaz de entender C++, En ves de eso, CPUS son solo capaces de procesar instrucciones escritas en lenguaje de machine( o código machine). El listado de todas las posibles lecturas de instrucciones en lenguaje de machine que un CPU puede leer o entender se llama una lista de instrucciones



Aquí esta un ejemplo de instrucción en lenguaje machine: 10110000 01100001.



Cada instrucción es entendido por el CPU como un comando para hacer un muy especifica cosa o trabajo, tal xomo "compara estos dos números" o "copea este numero en ese lugar de memoria". Hacia tiempo atrás, cuando las computadoras fueran creadas, programación tenían que escribir programas directamente en lenguaje de machine, el cual era muy difícil de hacer y consumía bastante tiempo hacerlo también.



Como ese que estas Instrucciones son organizadas y interpretadas esta mas allá de lo que buscan enseñarte estas series de tutoriales, pero no vale nada que le des unos intentos.



Primero, cada insrtucion esta compuesta de una sequencia de 1's y 0'. cada individual 0 o 1 es llamado un digito binario, o bit oara corto. El numero de bits en un listado de instrucciones de lenguaje de machine varian -- Por ejemplo, algunas CPUS procesan instrucciones que siempre son 32 bits de largo, Donde hay otras CPUS (tales como esas de x86 family, el cual puede que estes usando) tienen instrucciones que pueden ser de longitud variable.



Segundo, cada family de compatibles CPUS(ej.. x86, Arm64) tiene su propio lenguaje de machine, y ese lenguaje de machine no es compatible con el lenguaje de machine de otras families de CPU. Esto significa que programas escritas para un lenguaje de machine no pueden ser interpretadas y así correr en CPUS de una familia diferente!



### Contenido Relevante



Una Familia de "cpu´s" es formalmente llamado un "conjunto de instrucciones de arichitectura" ("ISA" para en corto). Wikipedia tiene un listado de diferentes Familias de CPU aquí.



lenguajes de Ensamblaje



Instrucciones de Lenguaje de Machine (como **1010000 01100001**) son ideales para un CPU, pero son difíciles para humanos entenderlos. ya que programas ( o al menos históricamente) han sido escritos y mantenidos por humanos, tiene sentido que lenguajes de programación deberían de ser diseñados con las necesidades humanas en mente.



Un lenguaje de ensamblaje ( usualmente llamado ensamblaje para en corto) es un lenguaje de programación que esencialmente funciona como un forma mas humanamente posible de leer lenguaje de machine. Aquí esta la misma instrucción de arriba en lenguaje de ensamblaje x86: **mov al, 0x61**.



### Lectura Opcional



Estas instrucciones illustran muchas de las capacidades que hacen un ensamblaje mas leeible que lenguaje de machine.



* La operación (lo que hace la instrucción) es identificada por un corto mnemonic (típicamente de 3-5 letra nombre). **mov** es entendido/identificado siendo un mnemonic para "mover" el cual es una operación que copea bits de una locación a otra.
* Registros (locaciones de memoria rápida que son parte del CPU mismo) son accedidos por nombre. **al**  es nombre de registro especifico en un x86 CPU.
* Numeros puden ser especificados en un formato mas conveniente. Lenguaje de Ensamblaje típicamente soportan ambos números decimales (ej.. **97**) y números hexadecimales (ej.. **0x61** ).



Es o seria bastante justo entender que la instrucción de ensamblaje  **mov al, 0x61** copee el número hexadecimal  **0x61** en el registro de CPU de  **al**

&#x20;

Ya que CPU¨S no entienden lenguaje de ensamblaje, programas de ensamblaje deben ser traducidos a lenguaje de machine antes de que puedan ser ejecutados. Esta traducción es hecha por un programa llamado assembler. Por que cada instrucción de lenguaje de ensamblaje esta típicamente diseñado para hacer lo mismo pero en otra instrucción de lenguaje de machine, el proceso de traducción es típicamente hecha sin mucho rodeo.



Justamente como cada Familia de CPU tiene su porpio lenguaje de machine, cada Familia de CPU también tienen sus propios lenguajes de ensamblaje ( el cual esta diseñado para ser ensamblado en lenguaje de machine para esa misma Familia de CPU). Esto significa que hay muchas differentes lenguajes de ensamblaje. aunque concepualmente similares, diferentes lenguajes de ensamblaje soportan diferentes instrucciones, usa diferentes conventiones de nombramiento, etc...



## Introducción a lenguajes de nivel bajo



lenguaje de machine y lenguaje de ensamblaje son considerados lenguajes de bajo nivel, ya que estos lenguajes proveen mínima arquitectura extraida del machine. en otras palabras, el lenguaje de programación mismo esta hecha a la medida para el especifico conjunto de instrucciones de arquitectura en la cual sera corrido.



Lenguajes de nivel bajo tienen un numero de najas notables:



* Programas escritos en un lenguaje de nivel bajo no son portables. ya que un lenguaje de nivel bajo esta hecho específicamente para un conjunto de instrucciones de arquitectura, el programa escrito en ese lenguaje lo será también. Haciendo porting de tales programas a hacia otras arquitecturas es usualmente no-trivial.
* Escribir o hacer un programa en lenguaje de bajo nivel en si es tener conocimiento detallado de arquitectura misma. Por instancia, las instrucciones **mov al, 061h** requiere saber que **al** se refiere al registro de CPU disponible en esta especifica plataforma, y entender como se trabaja con ese registro. en una arquitectura diferente, este registro podría ser nombrado de otra forma/manera, ten diferentes limitaciones, o no existas si quiera.
* programas de nivel bajo son difíciles de entender. mientras que ensamblajes individuales suelen ser bastante entendibles, aun así todavía puede ser difícil de deducir lo que una sección de código de ensamblaje realmente esta haciendo. y ya que programas de armados requieren muchas instrucciones para realizar incluso las tareas mas simples, suelen ser bastantes largas.
* Es difícil escribir programas de armado de complejidad significante por que el lenguaje solo provisiona capacidades primitivas. El programador es el que tendrá que implementar todo lo que necesite el mismo.



el beneficio primario de lenguajes de bajo nivel es que son rápidos, Armados siguen siendo utilizados hoy en día cuando hay secciones de código que son cruciales para el desempeño. y es usado también en otros casos, uno de los cuales discutiremos en brevedad.

Antes de C++, había solo C



El lenguaje C fue desarollado en 1972 por Dennis Ritchie en un Labotratorio de Teléfono Bell,PRIMARIAMENTE COMO UN lenguaje de programación de sistema( un lenguaje con el cual escribir sistemas operativos ). El principal motivo de Ritchie era producir un lenguaje minimilista con el cual seria fácil compilar, y que permitia eficiente acceso ala memoria, produjera código eficiente, y que fuera auto-contenido (no dependiente de otros programas). Para un lenguaje de nivel alto, lenguaje C fue diseñado para darle al programmador bastante control, mientras que permitia a desarrolladores escribir programa que podía correr en diferentes plataformas.



C acabo siendo tan eficiente y flexible que en 1973, Ritche y Ken Thompson rescirbieron la mayoría del sistema operativo de Unix usando C. Muchos sistemas operativos previos han sido escritos en ensamblaje. A diferencia de ensamblaje, el cual produce programa que solamente puede ser corrido en CPU¨S especificas, C tiene excelente portabilidad, permitiendo que Unix sea fácilmente compilado en muchas diferentes tipos de computadoras y incrementando su velocidad de adopción, C y Unix tenían  su fortuna unidos los dos juntos, y la popularidad de C era en gran parte amarrado al éxito de Unix como un sistema operativo.



En 1978, Brian Kernignan y Dennis Ritchie publicaron un libro llamado "El lrnguaje de programación C". Este libro, el cual era communmente conocido como K\&R ( nombrados asi por los últimos nombres del autor), provicionaron una informal especificaion para el lenguaje y se convirtieron en un standard de facto. Cuando máxima portabilidad era necesaria, programmadores solían apégarse a lo recommendado en K\&R, por que la mayoría de compiladores en el tiempo eran implementados a los standardes de K\&R.



En 1983, el Instituo de Standards Nacionales de America (ASNI) formaron un commite para establecer un standard formal para C. En 1989 (commites tomo demasiado para hacer lo que sea), ellos terminan, y sascan al publico el standard C89, mas communmente conocido com ANSI C. En 1990 La Organización Internacional para la Estandarelizacion (ISO) adopto ANSI C (con unas cuantas modificaciones menores). Esta versión de C se volvió conocida como C90. Compiladores eventualmente se volvieron ANSI C/C90 compiladores, y los programas deseando máxima portablidad eran codificados a este standard.



En 1999, El commite de ISO sacaron una nueva versión de C informalmente llamado C99, C99 ado´to muchas funciones las cuales ya habían llegado haciéndose camino como compiladores de extensiones, o que fueran implementadas por C++



## C++



C++ fue desarollado por Bjarne Stroustrup en los laboratorios Bell como una extensión de C.coomenzando en 1979. ### Step 4: Compiling your source code



In order to complie C++ source code files, we use a C++ compiler. The C++ compiler sequentially goes through each source code (.cpp) file in oyur program and does two important tasks:



First, the compiler checks your C++ code to make sure it follows the rules of the C++ language. If it does not, the compiler Will give you an error (and the corresponding line number) to help pinpoint what needs fixing. The compilation process Will also be aborted until the error is fixed.



Secon, the compiler translates yout C++ code into machine language instructions. These instructions are stored in an intermediate file called an object file. The object file also contains other data that is required or useful in subsequent steps /including data needed by the linkerin step 5, and for debuggung in step 7).



Object files are typically named name.o or name.obj, where name is the same name as the .cpp file it was produced from.



For example, if your program had 3.cpp files, the compiler would generate 3 object files:

|-|-|-|

C++ compilers are available for many diffrent operating systems. We Will discuss installing a  compiler shortly, so there is no need to do so now.



### Step 5 : Linking object files and libraries and creating the desired output file



After the compiler has successfully finished, another program called the linker kicks in. The linker´s job is to combine all of the object files and produce the desired output file (such as an executable file that you can run ). This process is called linking. if any step in the linking process fails, the linker Will generate an error message describing the issue and then abort.



First, the linker reads in each of the projects files generated by the compiler and makes sure they are vaild.



Second, the linker ensures all cross-file dependencies are resolved properly. For example, if yoy define something in one .cpp file, and then use it in a different .cpp file, the linker connects the two togeter, If the linker is unable to connect a refrence to something with it´s defenition, you´ll get a linker error, and the linking process Will abort.



Third, the linker typically in one or more library files, which are collections of precompiled code that have been "packaged up" for reuse in ither programs.



Finally, the linker outputs the desired output file. Typically this Will be an executable file that can be launched (but it could be a library fiile if that´s how you´ve set up your Project).

# 0.9 -- Configuring your compiler: Build configurations

A build configuration (also called a build target) is a collection of project settings that determine how your IDE will build your project. The build configuration typically includes things like what the executeable will be named, what directories the IDE will look in for other code and library files, whether to keep or stipe out debugging information, how much to have the compiler optimize your program, etc... Generally, you will want to leave these settings at their default values unless you have a specific reason to change something.

When you create a new project in your IDE, most IDEs will set up two diffrent build configurations for you: a release configuration, and a debugging configuration.

The debug configuration is designed to help you debig your program, and is generally the one you will use when writing your programs. This configuration turns off all optimizations, and includes debugging information, which makes your programs larger and slower, but much easier to debug. The debug configuration is usally selected as the active configuration by default. we´ll talk more about debugging techniques in a later lesson.

The release configuration is designed to be used when releasing your program to the public. This version is typically optimized for size and performance, and dosen´t contain the extra debugging information. Because the release configuration includes all optimizations, this mode is also useful for testing the performance of your code (which we´ll show you hoe to do later in the tutorial series).

When the Hello World program (from lesson 0.7) was built using VS code, the executable produced in the debug configuration was 65KB, whereas the executeable built in the release version was 12KB. The diffrence is largely due to the extra debugging information kept in the debug build.

Although you can create your own custom build configurations, you´ll rarely have a reason to unless you want to compare two builds made using diffrent compiler settings.

Best Practice
Use the debug build configuration when developing your programs. When you´re ready to release your executeable to others, or want to test performance, use the release build configuration.

Some IDEs (e.g. VS Code) also recreate separate build configurations for different plataforms. For example, VS code creates build configurations for both the x86 (32-bit) and the x64 (64-bit) platforms.

# 0.11 -- Configuring your compiler: Warning and error levels 

When you write your programs, the compiler will check to ensure you´ve followed the rules of the C++ language (assuming you´ve turned off compiler extensions, as per lesson 0.10), If you have done something that definitively violates the rules of the language, then your program is ill-formed.

In most cases, when the compiler encounters some kind of issue, it will emit diagnostic message (often called a diagnostic for short). The C++ standard does not define how diagnostic messages should be categorized, worded, or how those issues should affect the compilation of the program. How ever, modern compilers have conventionally adopted the following:

A diagnostic error (error for short) means the compiler has decided to halt compilation, because it either cannot proceed or deems the error serious enough to stop. Diagnostic errors generated by the compiler are often called compilation errors, compiler errors, or compile srrors.

A diagnostic warning (warning for short) means the compiler has decided not to halt compilation, in such cases, the issue is simply ignored, and compilation proceeds.

Key insight

COmpilers determine whether a non-blocking issue is a warning or an error, While they usally allign in their categorization, in some cases, compilers may not agree -- with one compiler emitting an error and another compiler emitting a warning for the same issue.

To help you identify where the issue is, diagnostic messages typically contain both the filename and the line number where the compiler found the issue, and some text about what was exécted vs what was found. The actual issue may be on that line, or on a preceding line. Once you´ve addressed the issue causing the diagnostic, you can try compiling again to see if the associated diagnostic message is no longer generated.

For advanced readers

We show an example of a statement that is technically legal but modern compilers find suspicious in lesson 7.7.

In rare cases, It may be necessary to explictly tell the compiler to not generate a particular warning for the line of code in question. C++ does not support an officail way to do this, but many individual compilers (including Visual Studio and GCC) offer solutions (via non-portable #pragma directives) to temporarily disable warnings.

Best practice

Don´t let warnings pile up. Resolve them as you encounter them (as if they were errors). Otherwise about a serios issue may be lost amongst warnings about non-serious issues.

The linker may also generate diagnostic errors if there is an issue that occurs when linking that cannot be resolved.

Increasing your warning levels 

By deafult, most compilers will only generate about the most obvious issues, However, you can request your compiler be more assertive about providing warnings, and it is generally a good idea to do so.

Best practice 

Turn your warning levels up, especially while you are learning. The additional diagnostic information may help in identifying programming mistakes that can cause your program to malfunction.

# 0.12 -- Configuring your compiler: choosing a languge standrad

With many diffrent versions of C++ available (C++98, C++03, C++11, C++14, C++17, C++20, C++23, etc...) how does your compiler know which one to use?
Generally, a compiler will pick a standard to default to C++14, which is missing many of the latest and greatest features.

If you wish to use a diffrent language standard (and you probably will), you´ll have to configure your IDE/compiler to do so.

The conventional names for language standard (e.g. C++20) are based on the year the language standard was published (or expected to be published).
Because the year of publication is not actually known until it is close, language standards that are early in development sometimes use a development name instead. For example, C++20 is also known as C++2a.

As an aside...

C++11 has development name C++0x because it was orginally expected to be published before 2010

Which language standard should you choose?

In professional environments, it´s common to chose a language standard that is one or two versions back from the latest finalized standrad (e.g.. if C++20 were the latest finalized version, that means C++14 or C++17). This is typicalle done to ensure the compiler makers have had a chance to resolve defects, and so that best practices for new features are well understood. Where revelant, this also helps ensure better cross-platform compartibility, as compilers on some platfrom may not provide full support for newer language standards immediately.

For personal projects and while learning, we recommend choosing the latest finalized standard, as there is little downside to doing so.

Tip 

Many compilers offer "experimental" or "preview" support for features from the upcoming non-finalized language standards. Your IDE may offer this as an option in the settings where you configure your language standard, or you may be able to enable it manually using the upcoming language standard´s conventional name or development name.

Support for features from non-finalized language standard will be incomplete and possibly buggy.

# 1.1 -- Statements and the structure of a program

Welcome to the first primary chapter of these C++ tutorials!

In this chapter, we´ll take a first look at a number of topics that are essential to every C++ program. Because there are quite a few topics to cover, we´ll cover most at a fairly shallow level (just enough to get by). The goal of this chapter is to help you understand how basic C++ programs are constructed, By the end of the chapter, you will be able to write your own simple programs.

In futture chapters, we´ll revisit the majority of these topics may be split over several subsequent lessons. If you feel like some important concepts isn´t covered in a lesson, or you have a question that isn´t answered in the current lesson, it´s possible that it´s covered in the next lesson.

Statements 

A computer program is a sequence of instructions that tell the computer what to do. A statement is a type of instruction that causes the program to perform some action.

Statements are by far the most coomon type of instruction in a C++ program. This is because they are the smallest independent unit of computation in the C++ language. In that regard, they act much like sentencesa do in a natural language. When we want to convey an idea to another person, we typically write or speak in sentences (not in random words or syllables). In C++, when we want to have our program do something, we typically write statements.

Most (but not all) statements in C++end in a semicolon. If you see a line that ends in a semicolon, it´s probably a statement.

In a high-level language such as C++, a single statement may compile into many machine language instructions.

For advanced reader

There are many different kinds of statements in C++:

Declaration statements
Jump statements
Expression statements
Compound statements
Selection statements (conditionals)
Iteration statements (loops)
Try blocks

By the time you´re through with this tutorial series, you´ll understand what all of these are!

Functions and the main function

In C++, statements are typically grouped into units called functions. A function is a collection of statements that get executed sequently (in order, from top to bottom). As you learn to write your own programs, you´ll be able to create your own functions and mix and match statements in any way you please (we´ll show how in a future lesson).

Rule

Every C++ program must have a special function named main (all lowercase letters).

When the program is run, the statements inside of main are executed in sequential order.

Programs typically terminate (finish running)after the last statement inside function main has been executed (though programs may abort early in some cicumstances, or do some cleanup afterwards).

Functions are typically written to do a specific job or perform some useful action. For example, a functions named max might contain statements that figures out which of two numbers is larger. A function named calculaterGrade might calculate a student´s grade from a set of test scores. A function named printEmployee might print an employee´s information to the console. We will talk a lot more about functions soon, as they are the most commonly used organizing tool in a program.

Nomenclature

When discussing functions, it´s fairly common shorthand to append a pair of parenthesis to the end of the function´s name. For example, if you see the term main() or doSomething(), this is shorthand for functions named main or doSomething respectively. This helps diffrentiate functions from other things with names (such as variables) without having having to write the word "function" each time.
