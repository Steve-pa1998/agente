SYNTAX ERROR: It's a Python error that means the interpreter encountered code that violates Python's grammar rules — it literally cannot parse/understand what you wrote.  It's raised during parsing, before execution begins.

Common causes:


Missing colon : after if, for, while, def, etc.


Unmatched parentheses (), brackets [], braces {}, or quotes


Misspelled or misused keywords (e.g., using class as a variable name)
Incorrect indentation


Missing or extra symbols (e.g., using = instead of == in a condition) 


Tip: The line Python points to isn't always where the actual mistake is — often the real problem is on the previous line (e.g., an unclosed parenthesis). Always check the line above the reported error. 





This error means you have a mismatched pair of brackets in your code.  Specifically, the opening symbol is a parenthesis (, but the code expects it to be closed by another parenthesis ).  Instead, it encountered a curly brace }. 

To fix this:

Check Line 56: Look for an opening ( that might be incorrectly closed with a }. 
Look Upward: The error often points to the closing mismatch, but the actual problem is the opening bracket on an earlier line (possibly before line 56) that was never properly closed. 
Verify Structure: Ensure that every ( has a matching ) and every { has a matching }. For example, x = (1, 2} is invalid because the ( requires a ), not a }.

x = (1, 2, 3}  # SyntaxError: closing parenthesis '}' does not match opening parenthesis '('

The fix:

x = (1, 2, 3)  # Correct: parenthesis matches parenthesis
# OR
x = {1, 2, 3}  # Correct: curly brace matches curly brace

A class is a blueprint for creating objects. It bundles data (attributes) and behavior (methods) together.

class Dog:
    # Class-level attribute (shared by all instances)
    species = "Canis familiaris"

    # Constructor (called when you create an instance)
    def __init__(self, name, age):
        self.name = name      # instance attribute
        self.age = age

    # Method (behavior)
    def bark(self):
        return f"{self.name} says woof!"

    def info(self):
        return f"{self.name}, {self.age} years old"

Key parts:
Part	Meaning
class Dog:	Declares a new type called Dog
__init__	The constructor — runs automatically when you create an instance
self	Refers to the specific instance (the object being created)
self.name	An instance attribute — unique to each object
Dog.species	A class attribute — shared across all instances
def bark(self)	A method — a function that belongs to the class

Creating an object:
rex = Dog("Rex", 3)
print(rex.bark())    # "Rex says woof!"
print(rex.info())    # "Rex, 3 years old"

Why use classes?
Organization — group related data + behavior
Reusability — create many objects from one blueprint
Encapsulation — hide internal details, expose a clean interface
Inheritance — create new classes that extend existing ones

Possible improvements / alternatives (just ideas, not recommendations to implement yet):

Add a short “specification” step between research and code-writing (a small document that lists exactly what the new agent should do, its tools, and constraints). You approve that spec before the code agent starts.
Have a lightweight coordinator that only routes messages and doesn’t do research or coding itself.
Optional later: a reviewer agent that only checks the generated code after you approve the spec.

About tool access (LLM, RAG, vector DB, tools, etc.)
This is the more important design choice.

Recommendation in principle:
Do not give every agent full access to everything by default.

Better approach:
Researchers / information gatherers → need RAG, vector DB, web/search tools, file reading.
Coordinator / planner → usually needs very few tools (or none). Its job is to talk to you and organize.
Code-writing agent → can have more tools (file writing, code execution, ability to look up libraries, etc.), but still better if it receives a clear spec instead of freely searching for whatever it wants while writing.

Why restricted access is usually better:

Less noise and fewer hallucinations.
Easier to control costs and behavior.
Clearer debugging (“this agent can only do X”).
You can still give the code agent a way to request a tool or information when it needs it, instead of giving it permanent access to everything.
